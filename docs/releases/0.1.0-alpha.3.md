> **Status boundary: release-state neutral.** This is the immutable
> release-facing projection for candidate version `0.1.0-alpha.3`; it neither
> announces nor denies mutable external release state. Verify that state only
> by joining the exact annotated tag and tracked lock with official npm
> bytes, provenance, complete dist-tag maps, and the GitHub Release record.
> D-050 is authorization, not execution evidence.

## Purpose and boundary

This candidate alpha demonstrates one trustworthy installed path from a
repository-owned synthetic POTX project to a native DrawingML card-arrow
candidate PPTX with a replayable build record and honest blocked QA. It is for
evaluating contracts, failure behavior, package boundaries, and contributor
workflow—not for general presentation production.

The public path does not provide the external render, independent-pixel, and
PowerPoint compatibility evidence required for delivery authority. It is not
arbitrary-template compatibility, a general renderer, delivery approval, or a
claim that any support row is `supported`.

## Fact ownership

The source template owns unchanged inherited content. Project JSON data and
`DeckSpec` own authored meaning. `SlideLayoutIR` owns editable constraints;
`ComposedSlidePlan` owns resolved geometry. `CandidateBuildRecord` binds both
to exact candidate bytes. `QaReport` records assessment, and only a later
passing final-delivery boundary may create `BuildArtifact`.

The support matrix owns claim status. The package plan owns intended tarball
contents and publication settings. The release plan and lock own exact
candidate identity. Release Gates owns phase order and eligibility. Official
npm and GitHub records own external lifecycle state. This note projects those
authorities; it replaces none of them.

## Candidate contents and flow

The candidate graph contains four packages:

- `pptx-compiler`: the explicit-root CLI;
- `pptx-compiler-core`: contracts, secure ingestion, dispatch, deterministic
  assembly, replay, and QA foundations;
- `pptx-compiler-native-card-arrow`: one exact native DrawingML capability;
- `pptx-compiler-public-synthetic`: the repository-owned conformance project.

Their installed path is:

```text
init public-synthetic project
  -> inspect exact bounded POTX
  -> validate complete graph and experimental support closure
  -> render one native-card candidate and CandidateBuildRecord
  -> qa re-derives and exact-compares both artifacts
  -> decision: blocked; no BuildArtifact
```

The renderer requires explicit experimental opt-in, derives placement from a
semantic slot, preserves source bytes, proves the allowed package diff, writes
the record before the PPTX commit marker, and never converts assembly success
into delivery authority.

## Executable contracts

- JSON Schema is normative for project, template, capability, deck, candidate,
  QA, and build records; generated TypeScript declarations are checked public
  consumers.
- Unknown versions, fields, inputs, features, relationships, bindings,
  platforms, and evidence fail closed.
- The exact capability registration binds metadata, executor, schemas,
  conformance cases, and QA assertions before invocation.
- Candidate generation and QA share the same layout derivation and compare the
  complete intent, plan, package diff, record, and PPTX bytes.
- Publication failures expose `not-committed`, `rollback-incomplete`, or
  `commit-uncertain` instead of hiding ambiguity.

## Release and provenance boundary

D-050 authorizes exactly version `0.1.0-alpha.3`, its annotated tag, dist-tag
`alpha`, public access, a matching GitHub prerelease, and GitHub Actions npm
provenance followed by the Trusted Publisher/bootstrap-token transition. It
does not authorize unpublish, movement of an old Git tag, reuse of an npm
version, or a separate `npm dist-tag add/rm` repair. The exact publish may
assign `alpha`, and npm may seed `latest` when creating a package identity.
None of those external facts is asserted by this note.

Both fixed builders must produce byte-identical canonical tar payloads. The
tracked lock records both builder-local gzip identities and allows only the
fixed Node 24/npm 11 envelopes to become release bytes. Registry absence
permits publishing only those bytes; exact presence permits continuation; a
mismatch stops permanently for that version.

Package identity, immutable package version, and package-level dist-tags are
verified separately. npm requires every package identity to have `latest`.
The intended post-`alpha.3` map is therefore:

| Package state before `alpha.3` | Required read-only postcondition |
| --- | --- |
| Existing `pptx-compiler-core` identity | `alpha -> 0.1.0-alpha.3`; frozen `latest -> 0.1.0-alpha.2` |
| First identity for each other package | registry-seeded `latest -> 0.1.0-alpha.3`; requested `alpha -> 0.1.0-alpha.3` |

Only the exact `npm publish --tag alpha` operation may assign `alpha` and
trigger npm's first-identity `latest` seed. The lane runs no separate dist-tag
mutation; unexpected tag state fails closed. Newly published bytes and attestations may become visible
at different times, so the workflow retries only bounded expected propagation
states before applying the exact certificate-bound Sigstore check. A timeout,
identity drift, malformed bundle, or bad signature remains a hard stop.

Credential cleanup begins only after the GitHub Release succeeds. The existing
`alpha-release.yml` workflow does not automatically modify npm or GitHub
settings; a local interactive npm 11.17.0 operator starts each exact package
with a fresh `npm trust list <exact-package> --json`. Empty permits one create
and fresh reread, exactly one normalized exact binding permits an idempotent
rerun, and any mismatch or other cardinality hard-stops. The exact readback maps
raw `type: "github"` to provider `github-actions`, raw `file:
"alpha-release.yml"` to the workflow filename, and sole `permissions:
["createPackage"]` to allowed action npm publish only; `createStagedPackage` is
forbidden. Owner `why7682`, repository `pptx-compiler`, and environment
`npm-release` must also match.

Only after four fresh exact bindings may a fresh `npm token list --json` let the
operator uniquely confirm the bootstrap token's full ID; ambiguity hard-stops.
Revoke it and fresh-prove it absent, then delete and fresh-prove absent only the
GitHub Actions environment secret `NPM_TOKEN` in repository
`why7682/pptx-compiler`, environment `npm-release`. Record no secret values.
npm does not validate a binding when it is saved, so configured/visible state
is not execution proof; a future tokenless OIDC publication is the first proof
that the binding works.

## Support state and limitations

The matrix remains 0 `supported`, 22 `experimental`, 3 `manual`, and 35
`unsupported`, with `supportClaimsEnabled=false`.

- Only the installation-owned public-synthetic POTX/profile is admitted.
- The CLI exposes one one-slide native-card candidate path and ends with
  blocked QA; it provides no general clone/fill, formula, chart, table, image,
  media, animation, or arbitrary DrawingML delivery.
- A trusted local PowerPoint observation is candidate- and version-specific;
  it does not establish public platform compatibility.
- The optional Pandoc adapter and all `labs/` planning/review experiments are
  outside the four-package graph and cannot authorize publication or support.
- Windows has no Node parent-directory fsync equivalent; sudden-power-loss
  directory-entry persistence is not claimed there.
- Public contracts remain `0.x`; no 1.0 stability promise exists.
- Main-branch protection remains separately deferred by D-047/M3-008.
